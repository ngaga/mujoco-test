# Two Stanford TidyBot robot modes

The same executable now selects one of **two explicit robot models**:

| Option | Model | Function |
| --- | --- | --- |
| `--robot tidybot` | **Full Stanford TidyBot (2023)**: mobile base, Kinova Gen3 7-DOF arm, Robotiq 2F-85 gripper, base and wrist cameras | Real MuJoCo model and small scripted joint movements; **no Kinova pick/place policy yet** |
| `--robot tidybot-so101` | Stanford TidyBot 2023 CAD base with **our SO-101 arm**, real jaw and front/wrist cameras | Existing experimental pick-and-place policies: oracle, RGB and RGB navigation |

Both modes share the official pinned Menagerie CAD base. The complete TidyBot mode additionally fetches the official Gen3/Robotiq mesh assets and tidybot.xml. All downloads are Git-SHA-verified and cached for offline runs.

### Commands (run from the repository root)

```bash
git pull --ff-only
python -m pip install -r requirements.txt -r mobile_demo/so101_requirements.txt
python -m mobile_demo.tidybot_full --fetch

# Full Stanford TidyBot with Kinova Gen3 and Robotiq
mjpython -m mobile_demo.so101 --robot tidybot --viewer --max-steps 400

# Stanford TidyBot base carrying our SO-101, with RGB navigation
mjpython -m mobile_demo.so101 --robot tidybot-so101 --perception rgb-nav --cubes 3 --viewer --max-steps 5500
```

The default is `--robot tidybot-so101` so existing SO-101 demo commands remain valid. `--require-success` and `--perception rgb/rgb-nav` apply only to the SO-101 hybrid: the full Kinova+Robotiq robot has different actuator dimensions, and we have not implemented its pick-and-place policy yet.

The current hybrid is experimental on the larger TidyBot chassis and may fail some physical cube tasks; this is explicitly reported rather than concealed. The original generic mobile demo is unchanged. This is the **2023 TidyBot**, not TidyBot++.

# SO-101 articulated arm on Stanford TidyBot CAD base (migration)

This experimental variant mounts the **same six-joint SO-ARM100/101 mechanical MJCF** used by our successful fixed-arm SmolVLA experiment onto the EarlyBots three-degree-of-freedom mobile navigator. It imports actual collision meshes, motors, two-jaw geometry, and TCP from the pinned upstream Apache-2.0 sim2cell package.

The original mobile_demo.run toy XYZ slide arm is NOT used by this variant. The Stanford TidyBot 2023 CAD hull is imported with its native visual and physical collision meshes, replacing the old LeKiwi-inspired decorative chassis. Asset downloads are SHA-checked against a pinned official Menagerie commit. This is still a planar position servo, not powered-caster physics; the large chassis has not yet passed the old physical success benchmarks. It has 9 commands: base x, base y, base yaw, then Rotation, Pitch, Elbow, Wrist_Pitch, Wrist_Roll, Jaw. The original base's physical XY/yaw navigation and two-stage route around the blue bin are retained.

**Honesty boundaries:** This is a physically articulated arm but still uses the simplified holonomic base with decorative wheels. Real omniwheel physics is future work. The arm policy is a scripted oracle with real DLS inverse kinematics, NOT pretrained VLA. The existing pretrained fixed-arm six-dimensional checkpoint cannot by itself navigate a nine-dimensional mobile robot. Cubes are reduced to 24 mm, matching the prior VLA workcell, so the original 48 mm benchmark cannot be compared directly. The real gripper can slip and drop, and the JSON report records those failures. The first single-cube strict physical rollout completed 1/1 at 22.7 s simulated (no retry). This is one deterministic sample, NOT a robustness claim. The arm mount at x=0.14 m and z=0.20 m is a kinematic research placement: it is near the upper outside edge of the proxy chassis and must be mechanically reviewed for a real build. The prior z=0.27 m mount could not reach the floor-level grasp.

## Start

Install from the repository root:

    python -m pip install -r requirements.txt -r mobile_demo/so101_requirements.txt

Verify the real imported model and cameras:

    python -m mobile_demo.so101 --check-model

Run one cube with physical contact, retries and JSON report:

    python -m mobile_demo.so101 --cubes 1 --max-steps 1000 --max-retries 2 --output mobile_runs/mobile_so101.json

Show the simulation in MuJoCo Studio WebViewer on macOS:

    mjpython -m mobile_demo.so101 --cubes 1 --viewer

The strict physical-delivery acceptance check is active in CI. It verifies a settled cube in the bin after real jaw release:

    python -m mobile_demo.so101 --require-success

## Blue-bin collision avoidance and oracle sensors

The five-cube control path now **avoids recapturing already-deposited cubes** during hover/descent and computes the TCP grasp height from the cube's actual Z position, not from a constant 18 mm above world floor. This avoids a previously observed jaw contact with the bin bottom during regrasp. No collision masks were disabled.

The dedicated `so101-bin-clearance.yml` workflow samples every actual MuJoCo physics step and fails if **any physical robot geom contacts the blue-bin geoms** or if any requested cube is not deposited. In the initial measured five-cube baseline there were 4,448 robot-vs-bin contact samples, involving the jaw and bin base with maximum penetration 0.8864 mm. With this change, the measured run deposited 5/5 cubes and recorded 0 such contact samples (and two retries). This is one deterministic rollout, not a guarantee across arbitrary positions.

**Which sensors are actually used?** This demo is an oracle-controlled robotics baseline. It reads MuJoCo's ground-truth free-body cube XYZ, arm joint position/state, and mobile X/Y/yaw joint state. Its simulated front and wrist RGB cameras exist but are not used by the grasp/navigation policy. It does not use LiDAR or a physical force sensor. The contact probe is diagnostic instrumentation, not an online sensor used to plan actions. This is not a vision-driven VLA run.
